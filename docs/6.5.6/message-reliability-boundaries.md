# 消息可靠性职责与本次简化

## 下行 QoS

- 重试任务只保存在始发节点内存，收到 ACK 或达到配置次数后结束。
- 默认重试 3 次，0 表示不重试；负数回落为默认次数，不再无限重试。
- 节点重启不恢复定时器，也不由其他节点接管。客户端重连或发现消息缺口时，主动按会话游标拉取历史，并按消息标识去重。
- 重试任务不写 Redis；已有消息正文、幂等状态、在线路由仍按各自职责使用 Redis，因此不是整个 QoS 流程零 Redis 访问。

## 入站消息与已读水位

- 同一 packetId 的热正文采用首次写入，重入复用已有正文；缓存命中不代表已提交，仍须完成索引和幂等提交。
- 首次正文写入从 Pipeline 中移出，以便重入时先确认正文再维护索引。首次命令数不增加，但增加一次独立往返；已有正文的重入增加一次 GET。
- 本次保证热正文不会被迟到请求覆盖；MQ 归档、Redis 热写及业务副作用仍不是跨存储事务，不能据此宣称整条消息链路 exactly-once。
- 冷库已读水位仅作为下限返回，由既有单调更新入口合并，回源过程中不再直接 SET 覆盖 Redis。

## 历史查询

- 聊天窗口只读 Redis 热索引。热索引到头是成功结束，不代表没有更早记录。更早的会话记录只查 Mongo。
- 窗口补拉使用 afterPacketId，只取严格大于本地最大消息号的热数据。查询失败保留游标。热索引下沿仍高于断线前的本地消息时，提示查看历史记录，不把 Mongo 页合并进窗口。
- 客服历史、IM Mongo 历史、会话列表和未读在存储异常时返回失败。正文缺条的热数据页同样失败。
- 客户端收到查询失败时保留原游标并允许重试；只有成功查询得到空结果，才可结束本次补拉或历史翻页。
- 外部渠道的业务投递仍使用现有流程，本次没有新增补偿队列、扫描任务或投递状态。

## 旧 Redis 数据

如果环境运行过 Redis QoS 恢复版本，全部旧节点退出后，可以一次性清理专用键 `ouyunc:qos:retry:pending`。
该旧 ZSET 本身没有键级 TTL，删除代码不会自动删除已有数据；专用 claim 键原有 TTL 为 30 秒，无须扫描清理。
本次仅修改源码，没有连接运行环境或删除 Redis 数据。

## 验收场景

1. 在线投递后不 ACK：重试达到上限停止；ACK 到达后取消，跨节点 ACK 仍可转发给始发节点。
2. 重启始发节点：没有 Redis 重试恢复，客户端通过历史补拉获得消息。
3. 两次相同 packetId 写入交错：后一次复用首次正文，不覆盖已经保存的内容。
4. 已读回源与新回执并发：最终水位不因旧数据库值回退。
5. Mongo 故障：历史分页及正文补全返回失败，客户端不推进游标；恢复后可继续查询。

编译与静态核对不能替代上述真实中间件和客户端联调验证。
